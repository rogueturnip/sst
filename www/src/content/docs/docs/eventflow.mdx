import { Tabs, TabItem } from '@astrojs/starlight/components';

[`EventFlow`](/docs/component/aws/eventflow) runs event-driven functions on [AWS Lambda durable functions](https://docs.aws.amazon.com/lambda/latest/dg/durable-functions.html), in your account. You write the functions with an API shaped like [Inngest's](https://www.inngest.com/docs/reference/typescript): send events, trigger functions with them, and write the functions as steps that retry, sleep, wait for other events, and invoke each other.

It's built on the [`Workflow`](/docs/component/aws/workflow) component, which stays as it is. Use `Workflow` when you start executions yourself. Use `EventFlow` when events should start them, and you want flow control per tenant, waits for events, and runs you can look up by ID.

:::tip
Moving from Inngest? Read [Migrate from Inngest](/docs/migrate-from-inngest) for what maps, what's different, and how to cut over.
:::

## How it works

You create an EventFlow once. It makes a fixed set of resources, and every function runs on them.

```txt
 send()                                                  ┌──────────────┐
 ─────▶ ┌───────────┐  batch  ┌────────┐  start run     │    Worker    │
        │   Queue   │ ──────▶ │ Router │ ─────────────▶ │  (durable)   │
        │ (SQS fair)│         └────────┘  resume wait   │ all functions│
        └───────────┘     ▲       │                     └──────────────┘
              ▲           │       │ dedup, leases, waits       │
   step.sendEvent()       │       ▼                            │
              └───────────┼─── ┌───────┐ ◀─────────────────────┘
                          │    │ Table │
          tick, each minute    └───────┘
          ┌──────────┐
          │ Schedule │
          └──────────┘
```

- **Queue.** A standard SQS queue, with a dead-letter queue. `send()` puts each event on it, with its tenant as the `MessageGroupId`, so SQS [fair queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-fair-queues.html) keep one tenant's backlog from holding up the others.
- **Router.** A Lambda function that reads the queue. For each event it skips duplicates, resumes the waits it matches, and starts a run of each function it triggers, after the function's rate limit, idempotency key and throttle allow it. It also serves the [admin API](#look-at-it-and-fix-it).
- **Worker.** One durable Lambda function that runs every function of the EventFlow. A run is one durable execution, and its name is the run ID.
- **Table.** A DynamoDB table for the engine's state: event IDs, concurrency leases and the steps waiting for them, throttle buckets, and waits. Every item expires.
- **Schedule.** An EventBridge schedule that ticks each minute, to start the functions with cron triggers.

The router and the worker run the same handler, the one `serve()` returns, and tell their work apart by what invokes them. So adding a function, or changing one, is a code change. Nothing is added to the infrastructure.

Every run starts through the router, including invoked runs, held runs, retries and replays. The router signs what it starts with a key only it and the worker have, and the worker runs nothing that isn't signed. See [security](#security).

### More than one

To run some functions apart from the others, create another EventFlow. Each has its own queue, router, worker, table and schedule. Do it when functions need:

- a different memory size, timeout, VPC or runtime;
- different permissions, so a function that handles payments can't read what another one can;
- to scale, fail or be deployed apart from the rest.

```ts title="sst.config.ts"
const flow = new sst.aws.EventFlow("Flow", { handler: "src/flow.handler" });

const media = new sst.aws.EventFlow("Media", {
  handler: "src/media.handler",
  memory: "4 GB",
  timeout: { invocation: "15 minutes" },
  schedule: false,
});
```

A function linked to more than one passes the one it uses: `new EventFlow({ id: "media", resource: Resource.Media })`. An event sent to one EventFlow doesn't reach the other, and `step.invoke()` only invokes functions of the same EventFlow.

## Events

An event has a `name`, `data`, and optionally an `id`, a `ts` and a `tenant`.

```ts
await flow.send({
  name: "contacts/import.requested",
  id: `import-${importId}`,
  data: { file, tenantId },
  tenant: tenantId,
});
```

- **Fan-out.** Every function with a trigger for the event's name starts a run, and every wait it matches resumes. A trigger can have an `if`, like `'event.data.plan == "pro"'`.
- **IDs and duplicates.** An event without an `id` gets a [ULID](https://github.com/ulid/spec). An event whose `id` was sent by the same tenant in the last **24 hours** starts no runs and resumes no waits. So when `send()` fails, send again with the same IDs. The same message delivered twice by SQS is routed again, and starts nothing new, and so is a message moved back from the dead-letter queue: see [delivery](#delivery-guarantees). An ID is 1 to 128 printable characters.
- **Tenant.** `tenant` is SST's addition to the envelope. It's the message's `MessageGroupId` for fair queues, and the router refuses an event whose tenant isn't its group. Event IDs, idempotency keys, run IDs, waits, and limits without a key are all kept per tenant. Events sent from a run with `step.sendEvent()` keep the run's tenant. A tenant is 1 to 128 letters, digits and punctuation, as SQS allows. Take it from something you trust, like the signed-in user, not the request body: see [security](#security).
- **Size.** An event is at most **1 MB** of JSON. Put large data in a bucket, and send its key.
- **Types.** `eventType()` declares an event with a [Standard Schema](https://standardschema.dev), like Zod. A trigger with it types `event.data`, and `create()` checks the data when it's sent. `staticSchema<T>()` declares the type only.
- `send()` returns `{ ids }`. Up to 10 events go in one SQS request.

The names `inngest/scheduled.timer`, `inngest/function.invoked` and `inngest/function.failed` are used for cron runs, invoked runs and `onFailure`, as with Inngest.

## Functions

```ts
flow.createFunction(
  {
    id: "import-contacts",            // stable: the run IDs come from it
    triggers: [{ event: "contacts/import.requested" }, { cron: "TZ=Europe/Paris 0 3 * * *" }],
    retries: 4,                       // per step, 0 to 20
    concurrency: [{ limit: 5, key: "event.data.tenantId" }, { limit: 50 }],
    throttle: { limit: 100, period: "1m", key: "event.data.tenantId" },
    onFailure: async ({ error, event, step }) => { /* ... */ },
  },
  async ({ event, step, runId, logger }) => { /* ... */ },
);
```

- **Triggers.** Up to 10. An event trigger, with an optional `if`. Its name can end in a wildcard, after a `/` or `.`, like `user/*`. A cron trigger, with 5 fields, in UTC or with a `TZ=` prefix, and an optional `jitter`, up to an hour, that spreads runs out. A function without triggers can only be invoked.
- **Cron.** The schedule ticks once a minute, and each cron trigger is checked against that minute. The run ID comes from the function and the minute, so a tick that's delivered twice starts one run. A tick that's lost isn't caught up.
- **Registration.** A function runs once it's in the list passed to `serve()`, and the EventFlow is deployed. `serve()` throws for two functions with the same ID.
- **Unsupported options throw.** `createFunction()` throws for an option EventFlow doesn't have, and for an expression it can't evaluate. It doesn't ignore them. See [what's not supported](#not-supported).

A function's context has `event`, `events` (more than one with [`batchEvents`](#batches)), `step`, `group`, `runId`, `logger`, `attempt`, `maxAttempts` and `idempotencyKey`. `attempt` starts at 0: in a step it's the step's, and outside of one it's the function's. Read it where you use it, as `ctx.attempt`: taken out of the context at the top of the function, it stays the function's.

### Expressions

Keys, `if`s and `priority` are [CEL](https://cel.dev) expressions, as with Inngest:

| | |
|---|---|
| Values | Paths like `event.data.items[0].sku` and `event.data["odd-key"]`, strings, numbers, `true`, `false`, `null`, lists |
| Operators | `==` `!=` `<` `<=` `>` `>=` `&&` `||` `!` `+` `-` `*` `/` `%` `in` `? :` |
| Functions | `has()` `size()` `string()` `int()` `double()` `bool()` |
| Of strings | `contains()` `matches()` `startsWith()` `endsWith()` `lowerAscii()` `upperAscii()` `trim()` `split()` `size()` |
| Of lists | `exists()` `all()` `exists_one()` `filter()` `map()` `join()` `size()` |

Anything else throws when the function is created. `matches()` takes a pattern as RE2 does, in time that's in proportion to the text, and without backreferences or lookaround: JavaScript's can take forever on text that a sender chooses. Order only compares numbers with numbers, and strings with strings, so a string can't pass `event.data.amount > 100`. A key can also be a function: `key: (event) => event.data.customerId`.

## Steps

```ts
const user = await step.run("load-user", () => db.users.get(event.data.userId));
```

A step's result is saved when it succeeds. When the run resumes, after a sleep, a wait or a crash, the handler runs again from the top, and each step that already succeeded returns its saved result without running. So:

- Put side effects, like API calls, writes, `Date.now()` and random IDs, inside steps.
- Do work in steps, not between them. Beside a branch that sleeps or waits, the function has half a second to come from one step to the next, before the run is paused until something wakes it.
- Keep the code between steps deterministic. The same inputs must call the same steps in the same order.
- A step's result is saved as JSON, so a `Date` comes back as a string.

### Retries

A step that throws is retried, up to the function's `retries`, which is **4** by default. So a step is tried at most 5 times. The backoff doubles from 2 seconds, with up to 50% jitter, to at most 10 minutes: about 1–2 s, 2–4 s, 4–8 s, 8–16 s.

- Throw `NonRetriableError` to fail the step now.
- Throw `RetryAfterError("…", "30s")` to choose when. It takes a duration, a `Date`, or a time string.
- A step that runs out of retries throws, with the error's message. Catch it to handle the failure, or let it fail the run. `onFailure` runs when the run fails.

An error thrown outside a step retries the function, up to its `retries`, with the same backoff. The next attempt goes on from the same steps: those that ended return what they did, or throw the errors they failed with, in the order the function had them, and those that hadn't, like a sleep or a step waiting for its next try, go on where they were. So nothing is done twice, and an `atMostOnce` step that started isn't started again. An error that came out of a step, a `NonRetriableError`, and a step used as it can't be aren't retried: the run fails. Before `onFailure` runs, the code of steps that's running ends, within a minute, and no step starts any more. `onFailure` is retried in the same way.

When the function returns, the code of steps it didn't wait for, like the loser of a race, ends before the run does, as long as the invocation lasts.

A step is **at least once**. If the worker crashes after the step's code ran, but before its result was saved, it runs again. Make side effects idempotent with `idempotencyKey`, or run the step `atMostOnce`: see [moving money](#moving-money).

### IDs

A step is found by its ID, as with Inngest, so branches that run at once can finish in any order. Used more than once, as in a loop, an ID gets the suffixes `:1`, `:2`, … in the order it's used.

A function is given its steps' results one at a time, and the order is saved with them. A replay gives them in the same order, so what depends on which step finished first is decided once: a `Promise.race` of a payment and a sleep, results handled as they come, a limiter, or two branches that use one ID. A failed function's next attempt has the same order too.

What isn't in a step has no order. Where branches that run at once do other work, like a `fetch` outside of a step, and then use one ID, which is which depends on that work, and can be another on a replay. The run fails when it's seen, which is when the first is still running, and otherwise one branch can get the other's result. Do the work in a step, or give the steps IDs of their own, like `` `charge-${order.id}` ``. When a replay doesn't call a step that's next in the order, the results after it wait for it, for 30 seconds. Then, if the same attempt called it, the run fails: its path depends on more than its event and its steps, like the time, or its code changed as it ran, as in `sst dev`, and going on could take another path than it did. If an earlier attempt, or the run it's a retry of, called it, the function goes on without it, with a warning in the logs.

A run stays on the version it started on: see [deploying](#deploying).

### Sleep

```ts
await step.sleep("wait-a-day", "1d");
await step.sleepUntil("wait-for-launch", "2027-01-01T09:00:00Z");
```

A sleep takes two of a run's durable operations: one to sleep, and one that saves when it ended, in the order of the function's steps. A duration is a number of milliseconds or a string like `"30s"`, `"5m"`, `"2h"`, `"1d"` or `"1w"`. It's rounded up to whole seconds. A sleeping run costs nothing, and can sleep until its [execution timeout](/docs/component/aws/eventflow#timeout).

### Parallel steps

Steps started together run together:

```ts
const [user, plan] = await Promise.all([
  step.run("user", () => getUser(id)),
  step.run("plan", () => getPlan(id)),
]);
```

### Signals

```ts
const approval = await step.waitForSignal("approval", { signal: `approve-${id}`, timeout: "3d" });

await flow.sendSignal({ signal: `approve-${id}`, data: { by: user.id }, tenant });
```

A signal goes to the one run of its tenant that waits for its name. A second run that waits for it throws a `SignalConflictError`, or takes its place with `onConflict: "replace"`. A signal that's sent before a run waits isn't kept. Its data is at most 200 KB. `step.sendSignal()` returns the `runId` it went to, if any. It's sent once for the run: a retry or replay of the run that sends it doesn't send it again.

### Fetch and AI

```ts
const res = await step.fetch("https://api.example.com/orders");          // a Response, saved
const answer = await step.ai.infer("ask", { model: openai({ model: "gpt-5" }), body: { messages } });
const summary = await step.ai.wrap("summarize", generateText, { model, prompt });
```

`step.fetch` is `fetch` as a step: the request runs in your worker, and its response, up to 700 KB, is saved. It's tried again when the request fails, not for an error status. `step.ai.infer` takes a model adapter, like those of [`@inngest/ai`](https://www.npmjs.com/package/@inngest/ai). It's tried again for a rate limit, when the provider says, or a server error. Unlike Inngest's, both wait in your Lambda, so they're billed while they do.

### Realtime

```ts
import { channel } from "@sst-community/eventflow";

const order = channel({ name: (id: string) => `order:${id}`, topics: { status: { schema: z.object({ state: z.string() }) } } });

await step.realtime.publish("tell", order(id).status, { state: "paid" });
```

Messages to browsers, through SST's [`Realtime`](/docs/component/aws/realtime) component, linked to the EventFlow. `step.realtime.publish()` publishes at least once, again where its step runs again, as after a crash or in a retry; `flow.realtime.publish()` now. Browsers subscribe with MQTT, to `flow.realtime.topic(order(id).status)`, which the component's authorizer has to allow. Inngest's subscription tokens and `useRealtime` aren't here. A message is at most 120 KB.

### Defer

```ts
const audit = createDefer(flow, { id: "audit" }, async ({ event, parents, step }) => { /* ... */ });

const deferred = defer("audit", { function: audit, data: { what: "paid" } });
```

A deferred function starts once the run that deferred it has ended, whether it succeeded or failed, and not if it was cancelled. `deferred.abort()` takes it back. Call `defer()` in the function, not in a step. Pass it to `serve()` with the others.

### Sessions

`send({ ..., meta: { sessions: { chat: chatId } } })` puts an event in sessions. A run's `sessions` are those that all of its events are in. The events it sends, and the functions it invokes, are in them too, unless the client has `sessionPropagation: false`; `null` takes one away.

### Another EventFlow's functions

```ts title="src/shop.ts"
new EventFlow({ id: "shop", resource: Resource.Shop, apps: { billing: Resource.Billing } });

await step.invoke("charge", { function: referenceFunction({ appId: "billing", functionId: "charge" }), data });
```

```ts title="sst.config.ts"
const billing = new sst.aws.EventFlow("Billing", { handler: "src/billing.handler", invokedBy: ["Shop"] });
const shop = new sst.aws.EventFlow("Shop", { handler: "src/shop.handler", link: [billing] });
```

The function it invokes has `external: true`. Anyone who may send events to its EventFlow can invoke it, so it takes its input as it takes an event's. Its result is at most 250 KB.

## Moving money

Payments, transfers and refunds have to happen once. A durable step is **at least once**: if the worker stops after the step's code ran, but before its result was saved, the step runs again. EventFlow gives you two ways to make that safe.

### Pass an idempotency key

Every function gets `idempotencyKey()`. Call it inside a step, and pass it to the payment provider, as most take one, like Stripe's `idempotencyKey`. It's the key of the step it's called in: the same in every attempt of the step, and in every [retry and replay](#retry-after-a-fix) of the run, and different for every other step and every other run. So a step that runs again makes the same request, and the provider does it once.

A step ID that's used more than once, as in a loop, has no key of its own: which use is which can be another in a replay, or a retry where a step before it now succeeds, and then one would be paid for with another's key. Say what it's of, like `idempotencyKey(order.id)`. Without that, `idempotencyKey()` throws in the second use, and the step fails. A key comes from the step's ID, so a step that's renamed has new keys: don't rename a step that has run, before you retry or replay its runs. In a step whose ID may be used more than once, always say what it's of: the first use can't tell that a second will come, and in a replay with another list it would have another's key.

It's made from the run's **root**, which the router makes from the first run's ID with the signing key, and signs into the run. So it can't be worked out from the event. A retry or replay keeps the root, so it sends the same keys. A run that another run invokes gets a root from its parent's, so a retry of the parent sends its child's keys again too. `onFailure` has keys of its own. The IDs of events a step sends are made the same way, from the step's ID and the event's place in what it sends, so a retried step, a crash, and a retry or replay of the run don't send them twice. So is the root of a run it invokes. Where a replay, or a retry, takes another path, as from a list that changed, a step ID that's used more than once can be another use's, and an event then has another's ID: give events an `id` of your own, like the order's ID, when you send them in a loop or a list. The router skips an event ID it has seen in the last 24 hours: a retry or a replay later than that sends them again.

```ts
flow.createFunction(
  { id: "charge-order", triggers: { event: "order/placed" } },
  async ({ event, step, idempotencyKey }) => {
    const charge = await step.run("charge", () =>
      stripe.paymentIntents.create(
        { amount: event.data.amount, currency: "usd", customer: event.data.customer, confirm: true },
        { idempotencyKey: idempotencyKey() },
      ),
    );
    await step.run("record", () => ledger.insert({ orderId: event.data.orderId, chargeId: charge.id }));
  },
);
```

Write to your own database the same way: an insert with the key as its primary key, or a conditional write, so a second try is a no-op.

### Or run the step at most once

For a call with no idempotency key, like some bank APIs, mark the step `atMostOnce`:

```ts
await step.run({ id: "wire", atMostOnce: true }, () => bank.sendWire(details));
```

AWS saves that the step started before its code runs. If the worker stops part way, the step isn't run again: the run fails with `StepInterrupted`, since the wire may or may not have been sent. It isn't retried when it throws, either. `sst eventflow run` says to check it.

A retry or replay that would run an `atMostOnce` step again is refused until you pass `--force`, after you've reconciled with the bank. A retry runs one again unless it reuses the step's saved result, so it's refused when the step didn't finish, threw, comes after the first step the retry runs again, or is in `onFailure`. A replay reuses nothing, so it's refused when one started at all. Runs the run invoked are checked too, since a rerun starts them again unless it reuses their result. It's all found in the histories, whatever the run's error says, so a run that timed out in the middle of the step is caught too.

### What was tested

On AWS, with a step that charges and then crashes the Lambda before its result is saved:

| Step | Provider calls | Charges | Run |
|---|---|---|---|
| With `idempotencyKey` | 2 | **1** | Succeeded: the step ran again, and the provider kept the first charge |
| With `idempotencyKey`, and a concurrency limit | 2 | **1** | Succeeded |
| `atMostOnce` | 1 | **1** | Failed with `StepInterrupted`, to reconcile |
| `atMostOnce`, and a concurrency limit | 1 | **1** | Failed with `StepInterrupted` |
| `atMostOnce`, then `retry --force` | 2 | **1** | Succeeded: the key is the same in the retry |

### Rules for money

- Every side effect goes in a step, with `idempotencyKey`, or `atMostOnce`. Never outside a step: that code runs again on every replay of the run.
- Give events from your system an `id`, like the order's ID, so sending one twice starts one run.
- Use `idempotency: "event.data.orderId"` on the function as well, to start one run per order in 24 hours, whatever the event IDs.
- `cancelOn` and `flow.runs.cancel()` stop a run where it is. The steps that ran aren't undone. Refund in `onFailure`, or in a step after a `waitForEvent`, not by cancelling. Once the function has returned or failed, an event no longer cancels the run: its `onFailure` and the run that invoked it aren't cut off.
- A replay runs every step again, with the same idempotency keys. A provider that keeps keys for a limited time, like 24 hours, may charge again after that: retry, which reuses the saved results, rather than replay. A retry runs again what comes after the first step it runs again, so give money steps keys that say what they're of, and retry within the provider's window.

## Waiting for events

```ts
const approval = await step.waitForEvent("wait-for-approval", {
  event: "invoice/approved",
  timeout: "3d",
  match: "data.invoiceId",
});
if (!approval) return "expired";
```

It returns the event, or `null` when none comes before the timeout. Its rules:

- **Correlation.** `match: "data.invoiceId"` matches an event with the same value there as the run's event. Or use `if`, where `event` is the run's event and `async` is the event that comes: `'async.data.invoiceId == event.data.invoiceId && async.data.amount > 100'`. The first `async.… == event.…` is looked up directly. Without one, every event of that name for the tenant is checked.
- **Only after it starts.** It only matches events received after the wait has registered. An event sent before isn't matched, as with Inngest.
- **The race.** An event that arrives while the wait registers is still matched. The wait and the router each write, then read: the wait registers, then reads the events since it started, and the router stores the event, then reads the waits. So for an event received after the wait started, at least one of them sees the other. This is checked in the tests, with an event delivered between the wait's two writes.
- **Tenants.** It only matches events with the run's tenant.
- **Duplicates.** An event delivered twice resumes a wait once. Many waits can match one event, and they all resume.
- **Timeout.** Up to the run's execution timeout. Events are kept for a wait that's registering for 1 hour, and waits are kept until they time out.

### Invoke

```ts
const receipt = await step.invoke("send-receipt", {
  function: sendReceipt,
  data: { orderId },
  timeout: "10m",
});
```

An invoked run's idempotency keys come from the step that invokes it. A step ID that invokes more than once, as in a loop, says what each is of, like `step.invoke("charge", { function: charge, data, idempotencyKey: order.id })`: in a replay with another list, one would have another's keys. Without it, the second use fails the run. A retry or replay of the run invokes the run again with the same keys. A function's own `idempotency` still applies to it: a retried invoke of a run whose key was taken in the last 24 hours is skipped, and the invoke fails. Adding `idempotencyKey` to a step that has invoked changes the keys of the run it invokes, so don't add it before you retry or replay runs that invoked without it. A function of another EventFlow gets new keys in each retry or replay of the run that calls it.

It starts a run of another function of the same EventFlow, waits for it, and returns what it returns. If that run fails, or doesn't finish within the timeout, it throws an `InvokeError`. The invoked run keeps the tenant, and its own flow control applies. A timeout doesn't stop it.

### Send events

```ts
await step.sendEvent("notify", { name: "invoice/sent", data: { invoiceId } });
```

### Cancel on an event

```ts
flow.createFunction(
  {
    id: "reminder",
    triggers: { event: "reminder/scheduled" },
    cancelOn: [{ event: "reminder/cancelled", match: "data.reminderId" }],
  },
  async ({ event, step }) => {
    await step.sleepUntil("wait-for-time", event.data.remindAt);
    await step.run("send", () => send(event.data));
  },
);
```

When an event in `cancelOn` matches, the run is stopped, even while it sleeps or waits. Its status is `STOPPED`, and the steps that already ran aren't undone. `match` and `if` work as they do for [waits](#waiting-for-events), with the same rules: only events of the run's tenant, received after the run started listening. The run starts listening before its first step, and stops when it ends. A `timeout` stops listening sooner.

The event IDs come from the run and the step, so a retried step sends the same IDs, and they aren't routed twice.

## Flow control

Flow control is set on each function. The three kinds limit different things.

| Option | What it limits | Over the limit | Where |
|--------|----------------|----------------|-------|
| `concurrency` | Steps running at once | The step waits in line for a lease | The worker, at each step |
| `throttle` | Runs started per period | The run is held, and starts later | The router |
| `rateLimit` | Runs started per period, by GCRA: a period's worth at once, then one each period ÷ limit, so up to twice the limit less one in a period from its start | The run is skipped | The router |
| `idempotency` | One run per key in 24 hours | The run is skipped | The router |
| `singleton` | One run per key at a time | The run is skipped, or the other cancelled | The router |
| `debounce` | One run once events stop | Earlier events are replaced | The router |
| `batchEvents` | One run for many events | The event waits for its batch | The router |
| `timeouts` | How long a run takes to start, and to finish | The run is cancelled | The router |

An event goes through them in this order: batch, rate limit, debounce, idempotency, singleton, throttle. A run that's invoked isn't debounced or batched.

### Concurrency

```ts
concurrency: [
  { limit: 5, key: "event.tenant" }, // each tenant
  { limit: 50 },                     // all tenants
],
```

- **What's counted.** A step that's running its code. Sleeps, waits, invokes and the code between steps don't hold a lease, so a run that sleeps gives its place to another. Steps started together each take one.
- **Scope.** `"fn"`, the default, counts the function's steps. `"env"` and `"account"` need a `key`, and count the steps of every function of the EventFlow with the same key value, like `key: '"openai"'` for a shared API.
- **Up to two, of up to 10,000 each.** A step has to fit both, for example 5 per tenant and 50 in all. It takes them one at a time, always in the same order, and gives back the first if the second is full. So a step never waits holding a lease, and two steps that need two limits, like a transfer that locks both accounts, can't each hold one and wait for the other. Each write is conditioned, so a limit can't go over, and none is a transaction: on a busy limit, transactions fail each other, where plain writes take their turn. A limit over 25 is split into shards, each a DynamoDB item, whose caps add up to the limit: so the writes of a wide limit aren't on one item, which takes 1,000 units a second. They share one line.
- **Leases.** Each attempt of a step takes a lease from the table before it runs, and gives it back when it ends. A retry takes a new one. A lease expires after the worker's invocation timeout plus 10 seconds, so a crash doesn't keep it. One that's given to a step in line lasts 3 minutes until the step resumes, which makes it its own before its code runs: from then on, nothing else gives it back. A step that resumes later than that asks again. A step that runs again after a crash renews its lease before its code runs, and takes a new one if it expired. A lease that expired is taken back only if it's still the one that expired, so it can't be taken from a step that just renewed it.
- **Waiting in line.** A step that doesn't get a lease joins the line for it, and its run stops, holding no Lambda. When a lease is given back, it goes straight to the next step in line, which resumes. If that step can't be told, as when the callback API throttles, it's tried again, and then put back in line, in its place. A newcomer can't take a free lease while steps wait. A step that isn't woken in 3 minutes, as when a wake was lost, asks again, and keeps its place in line. The longer it waits, the less often it asks, up to every 15 minutes, so a long wait doesn't fill its run's history.
- **Order.** A tenant's steps go in the order their runs' events came, so runs that have begun finish first. `priority: { run: "event.data.plan == 'pro' ? 120 : 0" }` moves a run up to 600 seconds ahead, or behind. A limit with shards gives to a few of the oldest at once, in any order.
- **Fairness.** Each tenant has its own line. The next step is the oldest of the tenant that holds the fewest leases on the limit, then the one that's waited longest. So a tenant with a backlog of thousands can't keep the others out. The tenant is the event's `tenant`, or the value of the function's concurrency key. It looks at up to 200 tenants in line for each lease. It's best effort: it doesn't promise a latency. [Measured below](#performance).

### Throttle

```ts
throttle: { limit: 100, period: "1m", burst: 10 },
```

Up to `burst + 1` runs start at once, then one each `period / limit`, so at most `limit + burst` in a period, as Inngest documents. A run over the throttle is given the next free slot, and goes back to the queue until it's due, up to 15 minutes at a time. So none are dropped, held runs come back one at a time in order, and a message delivered twice keeps its slot. It's the [generic cell rate algorithm](https://en.wikipedia.org/wiki/Generic_cell_rate_algorithm). Without a `key`, it's per tenant.

### Rate limit

```ts
rateLimit: { limit: 1, period: "1h", key: "event.data.userId" },
```

Up to `limit` runs start in each `period`. Runs over it are skipped, and logged. Without a `key`, it's per tenant. What was decided for an event is saved, so an event that's delivered again, after a start failed, isn't counted twice.

### Idempotency

```ts
idempotency: "event.data.orderId",
```

One run per key value, per tenant, in 24 hours. Others are skipped.

### Singleton

```ts
singleton: { mode: "skip", key: "event.data.accountId" },
```

One run at a time, of each key and tenant. With `"skip"`, another is skipped, and with `"cancel"`, the one that's running is cancelled. It's held while a run is held by a throttle, sleeps, or waits. A run that ended without giving it back, as when it was stopped, loses it to the next. A key that's `false` isn't a singleton.

### Debounce

```ts
debounce: { period: "10s", timeout: "1m", key: "event.data.documentId" },
```

The run starts once no event came for `period`, with the last one by its `ts`, or at the latest `timeout` after the first. Each key and tenant has its own.

### Batches

```ts
batchEvents: { maxSize: 100, timeout: "30s", key: "event.data.accountId" },
```

One run for up to `maxSize` events, 500 at most, or 10 MB of them, or those that came in `timeout`, in `events`. Each key and tenant has its own. Each event is in one batch, also when messages come again or a router stops part way. An event that `if` isn't true for starts a run by itself. It doesn't go with `idempotency`, `rateLimit`, `cancelOn`, `priority`, `debounce` or `singleton`, as with Inngest.

### Timeouts

```ts
timeouts: { start: "10m", finish: "1h" },
```

A run that hasn't started within `start` of its event, as behind a throttle or a concurrency limit, or hasn't finished within `finish` of starting, is cancelled. A step in flight isn't interrupted. `onFailure` doesn't run.

## Middleware

```ts
import { EventFlow, Middleware } from "@sst-community/eventflow";

class Tracing extends Middleware.BaseMiddleware {
  readonly id = "tracing";
  async wrapStepHandler({ stepInfo, next }) {
    return tracer.startActiveSpan(stepInfo.options.id, () => next());
  }
}

export const flow = new EventFlow({ id: "my-app", middleware: [Tracing] });
```

On the EventFlow, or on a function. It has the hooks of Inngest's: `transformFunctionInput`, `transformStepInput`, `transformSendEvent`, `wrapFunctionHandler`, `wrapStep`, `wrapStepHandler`, `wrapSendEvent`, `onRunStart`, `onRunComplete`, `onRunError`, `onStepStart`, `onStepComplete`, `onStepError` and `onMemoizationEnd`. A middleware's static `functions()` are served too. `wrapRequest` throws, since there's no request, and `stepInfo.memoized` is `undefined` before a step runs. `wrapFunctionHandler` and `wrapStep` run each time the function replays. The run hooks are a step each, so they run once, and one more operation.

## Events about runs

`inngest/function.finished` is sent for each run that ends, and `inngest/function.failed` or `inngest/function.cancelled`, where a function has a trigger for one. To wait for one in a step, send them for every run with `new EventFlow({ id, systemEvents: true })`. Runs they start send none, so they don't go on forever. A run that AWS ends, as one over its execution timeout, sends none. A sender can't send events whose names start with `inngest/`.

## Runs

A run's ID is its durable execution's name. It comes from the function's ID, and the event's ID and tenant, so it's known before the run starts.

```ts
const { ids } = await flow.send(orderPlaced.create(data, { id: `order-${orderId}`, tenant }));
const runId = flow.runs.idFor(processOrder, ids[0], tenant);
```

`flow.runs` finds runs by ID. It needs the [admin link](#look-at-it-and-fix-it): `link: [flow.admin]`. The EventFlow's own functions can use it only with `functionAdmin: true` on the EventFlow, so a function that's compromised can't cancel or rerun every run.

```ts
const run = await flow.runs.get(runId);
run.status;      // "RUNNING", "SUCCEEDED", "FAILED", …
run.steps;       // each step: its ID, type, status, attempts, times and error
run.failedStep;  // the first step that failed
run.links.logs;  // the worker's logs in CloudWatch

await flow.runs.list({ function: processOrder, status: "FAILED" });
await flow.runs.cancel(runId);
```

### Retry after a fix

A run that failed stays failed: AWS has no way to resume a failed durable execution. After you deploy a fix, **retry** it.

```ts
const { id, reused } = await flow.runs.retry(runId);
```

- A retry is a **new run**, with a new ID, of the same function and the same event, on the **latest deployed version**. Its `replayOf` is the run it retries.
- **The steps that succeeded aren't run again.** Their saved results, from the failed run's history, are returned in their place, by step ID: `reused` lists them. The step that failed, and everything after it, runs on the new code. So a charge that went through isn't made again.
- They're given in the order the run had them, up to the first step that's run again, like one that failed, even where the function caught it. After that the function may take another path, and a result found by its step ID could be another call's, so the steps after it run again, with the same idempotency keys. Give money steps keys that say what they're of, and retry within the payment provider's window for keys. An `atMostOnce` step after it is refused without `--force`.
- So it works, keep the IDs of the steps that succeeded. A step whose ID changed in the fix runs again.
- A step result over 800 KB in all, or one AWS truncated in the history, can't be reused. The retry says so; replay instead.
- **A run is retried once.** Retrying it again, as from a double click, or a script or a bulk retry that runs twice, returns the first retry, with `existing: true`, and starts nothing. Pass `again: true`, or `--again`, to retry it again on purpose.
- The retry keeps the run's [idempotency keys](#pass-an-idempotency-key).

Here a run failed at its fourth step, after the payment went through:

![sst eventflow run, a run that failed at book-carrier](../../../assets/docs/eventflow/cli-run-failed.png)

After the fix is deployed, the failed runs are retried:

![sst eventflow retry --failed](../../../assets/docs/eventflow/cli-retry-failed.png)

Only `book-carrier` ran again, on version 2. The payment's result is the one version 1 saved: it wasn't charged twice.

![sst eventflow run, the retry, with the steps it reused](../../../assets/docs/eventflow/cli-run-retried.png)

To run every step again, **replay** it:

```ts
const { id } = await flow.runs.replay(runId);
```

Every step runs again, including the ones that succeeded. Their side effects happen again, unless they're idempotent: use [`idempotencyKey()`](#pass-an-idempotency-key), which is the same in a replay.

To retry many, as after an outage:

```ts
await flow.runs.retryAll({ function: importContacts, status: "FAILED", from: new Date(Date.now() - 3_600_000) });
```

It takes up to 100 at a time, and returns each run's new ID, or why it couldn't. An invoked run can't be retried or replayed on its own: retry the run that invoked it.

Events the router couldn't route, after its retries, are in the dead-letter queue for 14 days. After a fix, move them back with `flow.admin.redrive()`, or `sst eventflow dead-letters --redrive`. They're routed again, as if they'd just been sent.

## Delivery guarantees

- **Events** are delivered at least once. An event that can't be routed is retried `retries` times (5 by default), about 6 minutes apart, then moved to the dead-letter queue, where it's kept for 14 days. A message that isn't valid, like one that isn't JSON, or whose tenant isn't its group, is dropped and logged, not retried.
- **Runs** start once per function, tenant and event. The run ID is the same each time, and Lambda starts one execution per name. That holds for as long as a run is kept, `retention`, 30 days by default.
- **Event IDs** are remembered per tenant for 24 hours. A second event with the same ID starts nothing.
- **Flow control** decides once per function and event, and the decision is saved: a delivery that's retried doesn't take a second slot.
- **Steps** are at least once, and their results are saved once. A step whose lease couldn't be given back doesn't run again.
- **Waits** resume once, with one event.
- **Invokes** always end: the invoking run hears back when the invoked run succeeds, fails, is skipped by its flow control, or is cancelled.
- **Ordering** isn't guaranteed. Events of different tenants can be routed out of order.

## Security

What EventFlow protects, and what it relies on you for.

- **Only the router starts runs.** It signs each run it starts, with a random key that only it and the worker may read. The key is in an SSM SecureString, not their environment, which anyone who can read a function's configuration sees. The worker refuses a payload that isn't signed, so a principal that may invoke the worker can't start a run around the router's checks, or answer another run's callback. Held and invoked runs in the queue are signed too, and expire after 15 days, longer than the dead-letter queue keeps them, so a copied message can't be sent again much later. When an invoked run's message expires, the run that invoked it is told.
- **Links are least privilege.** Linking the EventFlow grants `sqs:SendMessage` on its queue, and nothing else. `flow.admin` grants invoking the router, which can read every run and stop, retry and replay them. The worker and the router have only what they use. The functions can't use the admin API unless you set `functionAdmin: true`. That keeps a bug from cancelling every run; it's not a wall against harmful code in a function, which runs with the worker's permissions, including the signing key. Deploy only code you trust to the EventFlow's handler.
- **Bulk actions ask first.** `sst eventflow cancel --all`, `retry --failed` and `dead-letters --redrive` ask before they start, and need `--yes` without a terminal, as in CI.
- **The tenant is a label the sender asserts.** EventFlow keeps tenants apart, with per-tenant event IDs, idempotency keys, run IDs, waits and limits, and refuses an event whose tenant isn't its message group. But it can't check who a tenant is: anything that may send can send as any tenant. So set `tenant` from your own authentication, like the signed-in user's organization, in code you trust, and not from the request. Key flow control on `event.tenant`, not on a field of the data a caller chose.
- **Keys can't collide.** The table's keys hash their parts, so an event name or tenant with `#`, or anything else, can't reach another tenant's items.
- **Expressions run no code.** Keys and `if`s are paths, literals, comparisons and `&&`, evaluated on the event's own properties: a path can't reach a prototype. Ordering only compares numbers with numbers and strings with strings.
- **Bounded state.** Every table item expires. A concurrency limit's item keeps only the tenants that hold a lease, and each tenant in its line has an item of its own, so many tenants can't grow it.
- **Payloads stay in your account.** Events, step results and errors are in the queue, the table and the durable execution history, for `retention`. They're as sensitive as your data. The router logs event IDs and decisions, with keys hashed, not event data.

## Deploying

The worker is a published version. A run keeps the version it started on, through its sleeps and waits, so a deploy doesn't change runs in flight. New runs use the new version.

- **Changing a function's code** applies to new runs.
- **Changing a function's ID** makes it a new function. Its run IDs change, so an event sent again starts a new run.
- **Removing a function** stops new runs. Runs in flight finish on their version.
- **Replaying a run** uses the new version. If its steps changed, the replay follows the new steps.
- **The router** isn't versioned. A held throttle run of a function that's been removed is skipped and logged.
- **Removing an EventFlow** with runs in flight: `sst remove` stops each of them before it deletes the worker, one at a time, which takes a while with thousands. Stop them first, 10 at a time, with `sst eventflow cancel --all`.

## Cost

**Idle.** Under about **$0.50 a month**, mostly outside the free tiers:

- The queue's event source mapping polls it all the time, as Lambda's do: [AWS estimates](https://docs.aws.amazon.com/lambda/latest/dg/with-sqs.html) a few requests a minute per poller, about 650,000 SQS requests a month, or about $0.26.
- The schedule's tick, each minute: 43,200 EventBridge Scheduler invocations and as many short router invocations, about $0.05. With `schedule: false`, the schedule is disabled, and that's nothing.

The table and the functions are billed by use. These are estimates from AWS's pricing, not measured.

**A run.** A run started by an event, with two steps and a sleep, in _us-east-1_:

| | Use | Cost |
|---|---|---|
| SQS | send, receive and delete, in batches of 10 | $0.0000005 |
| DynamoDB | event ID write, waits read | $0.0000008 |
| Router | a tenth of an invocation, 512 MB | $0.0000003 |
| Durable operations | start, 2 steps, 2 for the sleep: 5 × $8 per million | $0.00004 |
| Worker | 2 invocations, 1 GB, about 100 ms each | $0.0000037 |
| **Total** | | **about $0.000045** |

What flow control and waits add:

- **Concurrency**, per step: 2 more durable operations (the child context, and taking the lease), and a few small DynamoDB reads and writes, about **$0.00002**. A step that waits in line adds 2 more, the callback and the step that joins the line, and its wake, about **$0.000035** with its DynamoDB reads and writes, plus 2 more operations for every 3 to 15 minutes it waits.
- **Throttle**, per run: a DynamoDB read and write, and an SQS message for a run that's held.
- **A wait for an event**: 3 durable operations, and 3 DynamoDB writes and a read, about **$0.000027**. Each event of a name that's waited for adds a write and two reads in the router.

Check [Lambda](https://aws.amazon.com/lambda/pricing/), [SQS](https://aws.amazon.com/sqs/pricing/) and [DynamoDB](https://aws.amazon.com/dynamodb/pricing/on-demand/) pricing for your region.

## Performance

:::note
These were measured before limits were split into shards. A limit of 20, as here, is one item as before.
:::

Measured on 2026-11-24 and 25 in _ca-central-1_, with the [AWS EventFlow tenants example](/docs/examples/#aws-eventflow-tenants): its defaults, 1 GB worker, 512 MB router, batches of 10. The load came from a Lambda function in the same region. Each step that's measured records its start and end in a table, and the example's `Report` function turns them into these numbers. Times are from `send()` returning to the start of the run's first protected step, so they include the queue, the router, starting the run, its first step, and taking a lease.

### Latency, unloaded

16 runs, 4 tenants, each round on its own, under every limit.

| Round | p50 per tenant | Worst |
|---|---|---|
| 1 | 0.48–0.61 s | 0.97 s |
| 2 | 0.36–0.58 s | 0.59 s |
| 3 | 0.39–0.48 s | 0.58 s |

A wait for an event resumed in **0.9 s at p50**, from sending the event to the next step starting, during the bursts below, where the next step had to take a lease again. In the [walk-through example](/docs/examples/#aws-eventflow), with no backlog, it was about 1.8 s, measured by polling `flow.runs.get`.

### A burst from five tenants, and a small one

Tenants `a`, `c`, `d`, `e` and `f` send 200 imports each at once, 1,000 in all. 10 seconds later, tenant `b` sends 10. Each import has two protected steps of 1 second, under `concurrency: [{ limit: 5, key: tenant }, { limit: 20 }]`. Five tenants at 5 each want 25 at once, so the shared limit of 20 is full. Tenant `b`'s imports also wait for a confirmation event, sent a minute later, and then take a lease again.

| | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| Runs finished, of 1,010 | 1,010 | 1,010 | 1,010 |
| Most steps at once, all tenants (limit 20) | 20 | 20 | 20 |
| Most steps at once, per tenant (limit 5) | 5 | 5 | 5 |
| Big tenants: wait to start, p50 | 41–47 s | 39–45 s | 38–44 s |
| Big tenants: wait to start, worst | 82 s | 75 s | 81 s |
| **Tenant `b`: wait to start, p50** | **2.5 s** | **2.3 s** | **2.4 s** |
| **Tenant `b`: wait to start, worst** | **3.7 s** | **3.6 s** | **3.4 s** |
| Wait resumed, p50 / worst | 0.9 s / 1.2 s | 0.9 s / 1.1 s | 0.9 s / 1.1 s |
| Backlog drained | 131 s | 129 s | 129 s |
| Leases, or steps in line, left after | 0 | 0 | 0 |

- **The limits held.** Never more than 5 steps of a tenant, or 20 in all, in any run.
- **A small tenant isn't stuck behind a big one.** Tenant `b` started within 4 seconds while the others' backlog took over 2 minutes.
- **The backlog drains at about 78% of the limit.** 2,020 step-seconds at 20 at once is 101 seconds; it took 129–131. A lease goes straight to the next step in line, but a woken run takes a moment to resume, and its lease sits idle until it does. Asking again on a timer, as an earlier version did, took 166–173, and with each lease in a DynamoDB transaction, 420 or more.
- **Throttle.** `notify-tenant`, at `limit: 60, period: "1m"` per tenant, started at most 61 runs in a minute for each tenant: the limit, plus the burst of 1.
- **A duplicate isn't run.** The 1,010 events of a burst from 8 hours before, sent again by mistake, started no runs.

### Cost under load

From the durable execution history of 300 runs of the bursts, and the table's consumed capacity:

| Run | Durable operations | Worker invocations |
|---|---|---|
| Big tenants, in the backlog | 15–17 | 3–4 |
| Tenant `b`, with a wait for an event | 25 | 6 |

About **$0.26** for a burst: the 1,010 runs and their notifications. $0.15 of durable operations at $8 per million, $0.07 of DynamoDB, 75,000 write units and 146,000 read units, and $0.04 of Lambda.

To reproduce it, deploy the tenants example and follow its steps.

## Not supported

These throw, when the function is created or they're used:

- Realtime's subscription tokens and `useRealtime`: browsers subscribe with MQTT
- `step.ai.models`: import the adapters from `@inngest/ai`
- backreferences and lookaround in `matches()`
- middleware's `wrapRequest`, and changing a step's ID in `transformStepInput`
- the client's `schemas`, which Inngest v4 hasn't either, and `endpointAdapter`

The [migration guide](/docs/migrate-from-inngest#compatibility) has what to use instead.
